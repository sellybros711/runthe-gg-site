# RunTheDrive — daily football drive

One drive a day. Read the defense, call the plays, chase the touchdown, keep
your streak alive. Lives at `runthe.gg/touchdown/`.

Every number in the game is measured from real football play-by-play and
charting data (2016–2025) — nothing is hand-waved. A skilled read lands a
touchdown ~35% of the time; spamming one call is measurably worse; reading down,
distance and the box is what separates the two.

## Files

| File | Role |
|---|---|
| `index.html` | The whole game UI (pixel-art, self-contained). Loads the three modules below, then drives the interactive flow. |
| `drive_generator.js` | Daily seed, starting field position, cosmetic weather, the **hidden defensive gameplan**, the per-snap defensive call, the pre-allocated blitz budget, and the generated scouting report. |
| `engine.js` | Play resolution, call **grading** (grades the decision, not the luck), the field-goal model, the interactive drive state machine, and the share card. |
| `playbook.js` | 6 schemes × 12 plays, every stat measured. Generated by `playbook_builder.py`; do not hand-edit. |
| `simulator.js` | Validation harness. `node simulator.js` plays thousands of deterministic drives under fixed policies and prints the outcome spread. |
| `playbook_builder.py` | The data pipeline that produced `playbook.js` (kept for provenance). |
| `HANDOFF.md` | The original design handoff — contracts, known issues, tuning notes. |

The handoff refers to `runthedrive_drive_generator.js` and
`runthedrive_simulator.js`; those are `drive_generator.js` and `simulator.js`
here (the engine `require`s them by those names).

## The one tuning knob

`DIFFICULTY` in `engine.js`. RunTheDrive has no punt — every 4th down is a
conversion attempt or a kick — which pushes scoring above real rates. This
single constant scales it back to the target. Solved by simulation, not guessed:

```
node simulator.js                 # current default
RTD_DIFFICULTY=-20 node simulator.js   # sweep to re-tune
```

At the shipped `DIFFICULTY = -3`: skilled ≈ 34.6% TD / 49.9% score, while a
quick-pass spammer drops to ≈ 20% TD with a ~71 call grade — because the
defense keys on tendencies, usage caps limit premium calls, and each play's
success is driven by its own measured success-by-distance curve. Change the
constant, re-run the simulator, read the new rate — that's the whole loop. The
simulator also prints a **per-scheme balance sweep** so you can see no single
playbook dominates.

## Contracts that must not break

1. **The defense never sees your play.** `defensiveCall(...)` has no play
   parameter — it reacts to down, distance and personnel only.
2. **Blitzes are a budget, not a coin flip.** `buildBlitzSlots()` pre-allocates
   a fixed count for the day, so the scouting report can describe exactly what
   you'll face and blitzes stay countable.
3. **Scouting lines are generated, never hand-written.** Every line renders from
   a live gameplan parameter, so it can't drift out of sync or state something
   false; uncertainty comes from withholding lines and banded language.
4. **Grade the call, not the outcome.** A great call that gets picked off still
   grades an A. That's what makes variance feel like football, not a con.
5. **`_hiddenGameplan` is server/logic-side only.** It never renders to the
   player as raw data — only through the scouting report and what they've seen.

## Persistence

Local only (`localStorage`, key `rtd:v1`): streak, best streak, coins, chosen
playbook, and per-day results. The daily drive is deterministic from the date,
so everyone plays the same defense on the same day. Practice drives use a random
salt and never touch the streak or coins.
